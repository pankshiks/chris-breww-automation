1.4 Critical Architecture Rules — Never Violate

  • Rule 1 — Breww native Xero integration is DEACTIVATED.n8n creates all invoices via the Xero API directly. The native integration has been deliberately turned off to prevent duplicate invoices. It must stay deactivated.
  • Rule 2 — Airtable is state, not pipeline.Airtable sits alongside n8n. n8n reads and writes Airtable for state tracking. Data does not flow through Airtable from one system to another. Correct: Breww → n8n → Xero with n8n reading/writing Airtable for state. Wrong: Breww → Airtable → Xero.
  • Rule 3 — Breww is the single source of truth for customer data.No other system overwrites Breww customer fields. Shopify details never overwrite Breww records. Sellar data never overwrites Breww records.
  • Rule 4 — Every workflow must implement loop prevention, idempotency, and retry.See Part 2 for the exact pattern. No exceptions.
  • Rule 5 — Never auto-create or auto-link a customer without confirmed match or human approval.Near/uncertain matches go to Airtable Review Queue. Humans decide. n8n acts on the decision.
  • Rule 6 — Breww custom fields are READ ONLY via API.You cannot write to Breww custom fields through the API (confirmed by Connor at Breww, Nov 2026 — existing feature request with Breww). Do not build any workflow that depends on writing to a custom field. Use the Breww Reference field (max 30 chars) for Consent ID storage, and use Airtable for all other integration state.
  • Rule 7 — Do not write VAT invoices from anywhere other than Xero.Gmail sends payment requests (Flow B) and order summaries only. These emails must be explicitly labelled "This is a payment request, not a VAT invoice." Xero is the only system that sends VAT invoices to customers.

Part 2

Universal Automation Rules

These five patterns apply to every n8n workflow. They are not optional. Claude must apply them to every workflow it builds.

2.1 Loop Prevention (Hash-Based Deduplication)

Two-way sync must not bounce changes indefinitely. Use this pattern on every sync operation:

Incoming event/payload arrives at n8n
        ↓
Extract only the fields n8n would write to the destination system
        ↓
Compute SHA-256 hash (canonicalize: sort keys alphabetically, lowercase string values)
        ↓
Read Airtable [Customer Sync or Invoice State] → Last Sync Hash for this record
        ↓
Compare hashes
        ↓
Same hash?  → STOP. Do not propagate. This was caused by our own last sync.
        ↓
Different hash? → Proceed
        ↓
Update destination system
        ↓
Write new hash to Airtable → Last Sync Hash
Write timestamp to Airtable → Last Synced At
// SHA-256 hash — Function node (Node.js crypto)
require('crypto').createHash('sha256').update(JSON.stringify(canonicalized)).digest('hex')

2.2 Idempotency

Every write operation must produce the same result whether run once or ten times.

  1. Before creating any record (Breww customer, Xero invoice, Airtable row), check if it already exists using the stored ID in Airtable.
  2. If it exists: skip creation, log "already exists", continue to the next step.
  3. If it does not exist: create it, store the new ID in Airtable, continue.

n8n: Airtable Search node → IF node: record found → skip; not found → create.

2.3 Error Handling and Retry with Exponential Backoff

AttemptDelay
1Immediate
230 seconds
32 minutes
410 minutes
After attempt 4Write "Failed" to Airtable, send alert

Use n8n's built-in Error Workflow pattern. Set Continue on Fail = ON on every HTTP Request node. After every HTTP Request, add an IF node checking for error. On error: call WF-ERROR-HANDLER.

2.4 Airtable State Write Pattern

Before any external action  → write status "Processing" or "Pending"
After success               → write status "Synced"/"Confirmed"/"Paid" + store IDs/hashes
On failure                  → write status "Retrying" or "Failed" + log error details

Never skip the pre-action write. If n8n crashes mid-operation, the pre-action status reveals where it stopped.

4.2 WF-ERROR-HANDLER — Shared Error Handler

Build this first — before any workflow that makes an API call. Every other workflow calls this sub-workflow on error.

Input parameters

{
  "workflowName": "string",
  "recordId": "string",
  "recordType": "Customer | Order | Invoice | Depot | Other",
  "operation": "string",
  "errorMessage": "string",
  "httpStatusCode": "number | null",
  "retryCount": "number (0-based)",
  "payload": "object (original payload to retry with)"
}

Node sequence

  1. Webhook / Execute Workflow Trigger — receives input from calling workflow
  2. IF: retryCount < 4? YES → continue to delay; NO → max retries exceeded branch
  3. Switch: retryCount — 0 → wait 30s, 1 → wait 2min, 2 → wait 10min, 3 → max retries
  4. Write Airtable: Error Log — Status: Retrying, all input fields, Retry Count: retryCount + 1
  5. Retry original operation — HTTP Request node with original payload (passed in)
  6. IF: retry succeeded? YES → Write Airtable: Error Log → Status: Resolved; NO → loop back to step 2 with retryCount + 1
  7. Max retries exceeded branch — Write Airtable: Error Log → Status: Failed, Alert Sent: true; Send alert email to admin; End

4.5 WF-A3-CUSTOMER-MATCH — Customer Matching Logic

Called by WF-A1-ONBOARDING-FORM. Run matching steps in this exact order:

Step 1 — Check Airtable for existing Breww ID

Search Customer Sync for submitted email OR VAT matching existing record with a Breww ID. If found → Outcome A.

Step 2 — Search Breww by VAT number

HTTP Request → Breww API: search customers by VAT. One result found → Outcome A.

Step 3 — Search Breww by normalised name + postcode

name
  .toLowerCase()
  .replace(/[^\w\s]/g, '')           // strip punctuation
  .replace(/\b(ltd|limited|plc|llp|trading as|t\/a)\b/g, '')
  .replace(/^the\s+/, '')
  .trim()
  • 1 result, name + postcode match → Outcome A
  • Multiple results OR name matches but postcode differs → Outcome B
  • 0 results → Step 4

Step 4 — Phone as supporting signal only

If two candidates and one shares phone → flag in Outcome B notes but still route to Outcome B (do not auto-confirm).

Step 5 — No match → Outcome C

Outcome A — Exact Match

  1. Update Airtable Customer Sync: Breww ID, Status: Synced
  2. Call WF-A3-ADMIN-APPROVAL with: outcome = A, Breww customer ID, Airtable record ID

Outcome B — Possible Match

  1. Airtable: Create record in Review Queue — Status: Awaiting Review, candidate Breww IDs, candidate names, match reason
  2. Send internal notification to admin team
  3. WF-A3-REVIEW-QUEUE-WATCH will pick up when status changes

Outcome C — No Match

  1. HTTP Request → Breww API: Create customer — Status: On Hold, Payment type: Pay in advance, Reference: Consent ID (max 30 chars — confirmed by Chris)
  2. Update Airtable Customer Sync: new Breww ID, Status: Pending
  3. Call WF-A3-ADMIN-APPROVAL with: outcome = C, new Breww customer ID, Airtable record ID
